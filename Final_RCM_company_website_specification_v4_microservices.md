# 36. Technology Stack & Hosting (ADDED)

This was not defined in the original spec. Recommended stack for a 5-page marketing site with a contact form and a careers/resume upload:

### Frontend
- Framework: Next.js (React) or a static site generator (Astro/Hugo) if no dynamic content is needed — either works for 5 pages; Next.js is preferable if Phase 2 (blog, client portal) is likely.
- Styling: Tailwind CSS, using the color/typography tokens in Section 4–5 as the design system config.

### Content management
- Decide **who edits content after launch** (marketing team vs. developer). Options:
  - Headless CMS (Sanity, Contentful, or a lightweight Git-based CMS) for job listings, case studies, blog.
  - Hard-coded content with developer-managed updates (fine for MVP given only 5 pages, but Careers/Open Positions will need frequent edits — a CMS or simple admin form is recommended even at MVP).

### Hosting & domain
- Static/JAMstack hosting: Vercel, Netlify, or AWS Amplify.
- Domain registrar and DNS provider to be confirmed.
- SSL/TLS certificate (auto-provisioned by most hosts) — HTTPS must be enforced site-wide, no mixed content.

### Form backend
- Where do submissions go? Specify one:
  - Transactional email (e.g., via SendGrid/SES) to business@ and careers@.
  - CRM integration (HubSpot, Zoho, Salesforce) for lead tracking.
  - Database + admin dashboard.
- Resume uploads (Careers page): specify accepted file types (PDF/DOC/DOCX), max file size (e.g., 5MB), and storage location (S3 or CMS asset store) with access restricted to HR.

# 37. Accessibility (ADDED)

Not addressed in the original spec. For an enterprise-positioned site this matters both for compliance and credibility.

- Target **WCAG 2.1 Level AA**.
- Keyboard navigation and visible focus states on all interactive elements (nav, buttons, form fields).
- All images require meaningful alt text (already noted for SEO in Section 29 — same requirement applies for accessibility, not just search).
- "Skip to main content" link for screen reader users.
- **Color contrast check needed:** Teal `#00A6A6` on white background (used for AI/technology accents) has a contrast ratio of roughly 2.7:1, which **fails WCAG AA (4.5:1) for normal text**. It's fine for icons, borders, or large decorative elements, but should not be used for body text or small labels on a white/light background.
- Form fields need associated `<label>` elements and clear inline error messages (not color-only indicators).

---

# 38. Legal & Compliance (ADDED)

Not addressed in the original spec, and directly relevant since the Contact form and Careers page collect personal data (name, email, phone, resume) and the company operates in the healthcare (RCM) space.

- **Privacy Policy and Terms of Use** — required at MVP launch, not deferred (see note in Section 33).
- **MVP privacy-law scope — India-first**: The website's initial Privacy Policy and data-handling requirements are defined for **India**, with the **Digital Personal Data Protection (DPDP) Act, 2023** as the primary privacy framework. The policy should cover the site's collection and processing of contact details, enquiry information, and candidate/resume data, including notice/consent where applicable, specified purposes, retention, security, and deletion/rights processes. The implementation should also account for the applicable DPDP Rules and related requirements in force at launch.
- **GDPR/CCPA are not part of the MVP compliance scope by default.** Do not add GDPR/CCPA requirements merely because the public website may be reachable from Europe or the United States. If the company later intentionally targets customers, candidates, or other data subjects in jurisdictions where those laws apply, the Privacy Policy, cookie/tracking approach, forms, data-processing arrangements, and related controls should be reviewed and expanded before that market launch.
- **Cookie consent banner** if analytics/tracking cookies are used (Section 34 lists "Analytics" as an MVP item — this triggers a consent requirement in most jurisdictions).
- **No PHI on the marketing site**: because "RCM Healthcare" is a service line, add an explicit note (e.g., in the Contact form's fine print) that the form is for business enquiries only and should not be used to submit patient health information. This protects the company from inadvertently receiving PHI through an unsecured channel.
- Resume data retention policy for Careers submissions (how long resumes are stored, and how a candidate can request deletion).

# 40. Form Security & Spam Protection (ADDED)

Section 25 says "protect against spam" and "store submissions securely" without specifying how.

- Use a CAPTCHA/anti-bot solution (Google reCAPTCHA v3, hCaptcha, or a honeypot field) — pick one.
- Rate-limit submissions per IP.
- Sanitize and validate all inputs server-side (not just client-side) before storage or forwarding.
- If storing submissions in a database, ensure encryption at rest and restricted access (ties to Section 38 compliance needs).

# 41. Performance & Browser Support (ADDED)

Section 28 says "fast page loading" without a target, and no browser matrix is defined.

- Performance target: Core Web Vitals in the "Good" range (LCP < 2.5s, CLS < 0.1, INP < 200ms) on 4G mobile.
- Image optimization: serve responsive/compressed images (WebP/AVIF with fallback), lazy-load below-the-fold images (hero image on Home should NOT be lazy-loaded).
- Browser support: latest 2 versions of Chrome, Safari, Edge, Firefox; iOS Safari and Android Chrome for mobile.

# 49. Architecture Decision — Microservices (SUPERSEDES SECTIONS 36 & 45)

**This section overrides the simple static/monolithic hosting guidance in Sections 36 and 45.** The project will be built as a **microservices-based, containerized backend** with a separate frontend application, so that each business capability is an independently deployable service from day one.

## 49.1 Why (rationale for the coding agent)

Sections 33/34 already describe a future roadmap: a client portal, an RCM platform, supply chain analytics products, self-service client tools, and a recruitment platform (Phase 2/3). Building the backend as discrete services now — rather than as a single monolith — means each of those future products can be added as a new service that plugs into the same API Gateway and event bus, without rewriting the existing site.

## 49.2 Fixed technology decisions (no alternatives — build exactly this)

To remove ambiguity for an autonomous build, the following choices are final and replace any "or"-style options mentioned earlier in this document (e.g., Section 36's CMS/hosting options, Section 39's analytics-tool options):

| Frontend framework | Next.js (React, TypeScript) |

| Backend language/runtime | Node.js 20 LTS + TypeScript |
| Backend framework | Fastify |

# 52. Per-Service API Specifications

## 52.1 `content-service`

```text
GET  /api/v1/content/home
GET  /api/v1/content/about
GET  /api/v1/content/technologies
GET  /api/v1/content/case-studies
GET  /api/v1/content/case-studies/{id}

PUT  /api/v1/content/{page}        (requires JWT, role: marketing|admin)
```

`content_db` schema (minimum): `pages(id, slug, title, body_json, updated_at, updated_by)`, `case_studies(id, title, summary, flow_diagram_json, published, created_at)`.

## 52.2 `contact-service`

```text
POST /api/v1/enquiries
Body: { name, company?, email, phone?, interest[], message, captchaToken }
Response 201: { id, status: "received" }
```

Behavior: validates required fields and email format server-side, verifies `captchaToken` against the CAPTCHA provider, persists to `contact_db.enquiries`, publishes `enquiry.created` to SQS with the enquiry `id`. Does **not** call SES directly — that is `notification-service`'s job.

`contact_db` schema: `enquiries(id, name, company, email, phone, interest_categories[], message, status, source_ip_hash, created_at)`.

## 52.3 `careers-service`

```text
GET  /api/v1/jobs
GET  /api/v1/jobs/{id}
POST /api/v1/jobs/{id}/apply     (multipart/form-data: name, email, phone, resume file, captchaToken)
Response 201: { applicationId, status: "received" }

# Admin-only, requires JWT (role: hr|admin):
POST   /api/v1/jobs
PUT    /api/v1/jobs/{id}
DELETE /api/v1/jobs/{id}
GET    /api/v1/applications
```

Behavior: validates resume file type (PDF, DOC, DOCX only) and size (max 5MB), uploads to the `careers-resumes` S3 bucket under `applications/{applicationId}/resume.{ext}`, persists candidate record to `careers_db`, publishes `application.created` to SQS.

`careers_db` schema: `jobs(id, title, location, employment_type, experience, skills[], description, active, created_at)`, `applications(id, job_id, candidate_name, email, phone, resume_s3_key, status, created_at)`.

## 52.4 `notification-service`

Subscribes to the SQS queue for `enquiry.created` and `application.created`. On `enquiry.created`, sends the enquiry to `business@[company-domain]` via SES using a fixed HTML template and a confirmation email to the submitter. On `application.created`, sends the application to `careers@[company-domain]` and a confirmation to the candidate. No public HTTP endpoints; health check only (`GET /health`).

## 52.5 `admin-service`

```text
POST /api/v1/admin/login          Body: { email, password } → { token }
GET  /api/v1/admin/me             (requires JWT)
GET  /api/v1/admin/enquiries      (requires JWT, role: business_dev|admin)
GET  /api/v1/admin/applications   (requires JWT, role: hr|admin)
```

`admin_db` schema: `users(id, email, password_hash, role, created_at)` with roles: `marketing`, `hr`, `business_dev`, `admin`.

# 53. API Gateway Routing Rules

```text
/api/v1/content/*        → content-service   (public GET, JWT-protected PUT)
/api/v1/enquiries         → contact-service    (public POST, rate-limited: 10/min/IP)
/api/v1/jobs*             → careers-service    (public GET/POST, rate-limited on POST: 5/min/IP)
/api/v1/admin/*           → admin-service      (login public, all else JWT-protected)
```

All routes enforce HTTPS only. All `POST` routes require a valid CAPTCHA token verified at the gateway (or at the receiving service, consistently — pick the service-level check to keep the gateway thin) before forwarding to the backend service.

---

# 54. Inter-Service Communication

- **Synchronous**: `web-frontend` → `api-gateway` → individual service, over HTTPS/JSON. Services never call each other synchronously and never share a database.
- **Asynchronous**: `contact-service` and `careers-service` publish events to a single SQS queue (`site-events`); `notification-service` is the sole consumer. This decouples email/CRM delivery from the user-facing request, so a slow or failed SES call never blocks the enquiry/application response to the user.

Event payload shape (both event types):

```json
{
  "eventType": "enquiry.created",
  "id": "uuid",
  "occurredAt": "ISO-8601 timestamp",
  "data": { "...service-specific fields..." }
}
```

---

# 55. Data Architecture — Database per Service

Each service owns its own PostgreSQL database (or schema, within one managed instance for MVP cost efficiency). No service ever queries another service's database directly. If a future dashboard needs a cross-service view (e.g., "all enquiries + all applications this month"), it must be built as a new read-only reporting service that consumes the same SQS events and maintains its own read model — never by granting cross-database access.

# 60. Observability

- **Logs**: every service logs structured JSON to stdout; ECS ships this to CloudWatch Logs automatically. Log group per service.
- **Traces**: OpenTelemetry SDK in every backend service, exporting to AWS X-Ray, so a single enquiry submission can be traced from `api-gateway` → `contact-service` → SQS → `notification-service`.
- **Metrics**: CloudWatch Metrics (request count, error rate, p95 latency) per ECS service, visualized in a shared Grafana dashboard.

# 61. Security in the Microservices Context

- The API Gateway is the **only** public entry point to the backend; all ECS services sit in private subnets with no public IPs.
- `admin-service` issues short-lived JWTs (1-hour expiry); all admin routes on other services validate the JWT at the gateway before forwarding.
- Public routes (`/api/v1/enquiries`, `/api/v1/jobs*` POST) remain unauthenticated but are CAPTCHA-protected and rate-limited at the gateway.
- Secrets (DB credentials, JWT signing key, SES/CAPTCHA API keys) live in AWS Secrets Manager and are injected into each ECS task as environment variables at deploy time — never committed to the repo.
- Each service's ECS task role follows least privilege: `careers-service` can read/write only its own S3 bucket and its own database; `content-service` cannot access `contact_db` or `careers_db`, and so on.
- All traffic between the API Gateway and ECS services, and between services and their databases, is encrypted in transit (TLS).
